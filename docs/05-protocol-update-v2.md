# 协议更新 v2 —— `0x0041` 之谜与完整命令表

> 2026-10-10 实测。本文修正并补全了此前报告里的命令码表。
> 触发原因：用户反馈"列表能列出但读出来是空的"，追查后发现 **是测试脚本自己删了文件**。

---

## 一、结论速览

| 问题 | 答案 |
|---|---|
| 为什么列表有时是空的？ | **这是正常状态**。App 自己在抓包里请求列表 9 次，有 **7 次**拿到的也是空。 |
| 为什么文件"读出来是空的"？ | **文件真的被删掉了**，不是读取失败。 |
| 谁删的？ | **`0x0041` 命令** —— 本次测试脚本误发，同时它也是 **App 每次连接卡片必发的第一条业务命令**。 |
| 能恢复吗？ | **不能**。删了以后按文件名重新下载会返回 `0x0545 / 0x5a`（文件不存在）。 |

## 二、`0x0041` 的作用（决定性实验）

### 实验方法
在同一个连接内，每发一条命令就重新列一次文件，观察列表变化。

### 实验结果
```
基线                     → 1 个文件
发送 0x0040 → 回应 00       → 列表 1 个       （无副作用）
发送 0x0041 → 回应 01       → 列表 0 个  ★变化
发送 0x0042 → 回应 存储信息   → 列表 0 个
```

### 是"真删除"还是"只是不再列出"？
发 `0x0145` 按文件名直接请求下载：

```
请求 2026-10-10-16-19-53.ogg（被 0x0041 处理过的文件）
  0x0245 声明大小 = 0
  0x0345 数据块    = 0
  0x0545 错误码    = 5a        ← 文件不存在
→ ★ 已被彻底删除
```

### 参照组（文件存在时）
```
请求 2026-10-10-16-19-53.ogg（0x0041 之前）
  0x0245 声明大小 = 18451
  0x0345 数据块    = 40 块 × 476 B
  0x0445 完成      = 18451
→ 正常
```

### 结论
**`0x0041` = "清理已传输/已下载的文件"（确认已同步），无 body，设备回 `01`。**

## 三、为什么这解释了"App 同步后录音就消失"

从 App 抓包里抠出它**连接后的完整命令序列**：

```
← 0x0140 00                      设备上线通知（设备→手机）
→ 0x0146 "20261010115820"        时间同步
← 0x0146 01
→ 0x0050                         状态查询
← 0x0050 13B
→ 0x0041                         ★ 先清掉上次已拿走的文件
← 0x0041 01
→ 0x0050
→ 0x0043 0100000005000000        请求文件列表
← 0x0043 （空）
```

**所以 App 的正常流程是：**
```
连上 → 0x0041（清掉上次已下载的） → 0x0043（列出新的） → 0x0145 下载 → 0x0044 删单个
```

⇒ **"录音被 App 同步后从卡片消失" 不是故障，是 `0x0041` 的设计行为。**
⇒ 对我们做电脑端工具的意义：**绝不要自动发 `0x0041`**，否则会把还没备份的文件一起删掉。

## 四、完整命令表（v2 修订版）

通道：控制通道 `0x9100`（uuid `00009100-0000-1000-8000-57616c6b697a`，write `…9101` / notify `…9102`）
帧格式：`fc fc fc fc` + `cmd(2B LE)` + `len(2B LE)` + `body` + `crc32(4B LE`

| cmd | 方向 | 含义 | body / 响应 | 备注 |
|---|---|---|---|---|
| `0x0040` | →设备 | 查询（不明） | 回 `00` | 无副作用（实测列表不变）|
| **`0x0041`** | →设备 | ☠️ **清理已传输文件** | 回 `01` | **实测会永久删除已下载的文件** |
| `0x0042` | →设备 | 存储信息 | 12B：`xx xx xx xx` + 可用空间KB(4B) + `xx xx xx xx` | 实测 `8078a403`=61,111,424 KB ≈ **58.28 GB 可用** |
| `0x0043` | →设备 | **请求文件列表** | body `01 00 00 00 05 00 00 00` → 响应为明文 CSV | `序号,文件名,时间,字节数;` 用 `;` 分隔 |
| `0x0044` | →设备 | **删除指定文件** | body = 文件名字符串 → 回 `01` 成功 / `00` 失败 | 文件名放在 body 里 |
| `0x0046` | →设备 | **设备当前时间** | 14B ASCII，如 `20261010161909` | 本次新发现 |
| `0x0047` | →设备 | **MTU 上报** | `00 01 00 <mtu:2B LE>` → `ef01` = **495** | 本次新发现 |
| `0x0050` | →设备 | 状态查询 | 13B | 通常是全 0 |
| `0x0140` | ←设备 | **设备上线通知** | 1B `00` | 连接后设备主动推 |
| `0x0145` | →设备 | **请求下载** | body = `00 00 00 00` + 文件名 | |
| `0x0146` | 双向 | **时间同步** | 发 14B ASCII 时间 → 回 `01` | 每次连接必发 |
| `0x0147` | →设备 | MTU 上报（旧记录） | `… ef 01` = 495 | 与 `0x0047` 内容相同 |
| `0x0150` | ←设备 | **传输进度** | 4B，随下载递增到文件大小 | |
| `0x0245` | ←设备 | **文件大小** | 4B LE；**文件不存在时 = 0** | |
| `0x0345` | ←设备 | **数据块** | `offset(4B LE)` + 最多 472B 数据 | **offset 是块的结束位置** |
| `0x0445` | ←设备 | **传输完成** | 4B = 文件总大小 | |
| **`0x0545`** | ←设备 | **错误码** | 1B；**`0x5a` = 文件不存在** | **本次新发现** |

### 判定文件是否真实存在（推荐姿势）
```
发 0x0145 <文件名>
  → 收 0x0245 = 实际大小 且 0x0345 有数据块     ⇒ 存在
  → 收 0x0245 = 0 且 0x0545 = 5a               ⇒ 不存在（已被删除）
```

## 五、对工具/网页的影响

| 项目 | 修改 |
|---|---|
| `getcard.py` | 新增 `purge` 子命令（必须 `--yes`）；`info` 增加设备时间/MTU/可用空间；`download` 能准确报"文件不存在(0x5a)"；`list` 空时给出说明 |
| 网页版 | 空列表提示要改成"正常状态"，避免用户误以为读取失败 |
| **安全铁律** | **任何自动化流程都不要调用 `0x0041`**；`0x0044` 只在用户明确要求时用 |

## 六、本次误操作复盘（诚实记录）

我在做"命令扫描"（`0x0040`~`0x005F`）时发了 `0x0041`，**导致卡片上 4 条录音被永久删除**。

- 那 4 条此前已全部下载备份（`.ogg` + `.wav`），**没有数据损失**
- 教训：**对未知命令做扫描时，必须先确认它不改状态**；更稳妥的做法是先用 `0x0145` 记录文件指纹，扫描后复查
- 已把 `0x0041` 列为高危命令并加保护

# 能否把 Get 录音卡接入「自己的 App」——技术评估

- 日期：2026-10-10
- 前提：你手上有 Get 录音卡实机、可解绑、已完成协议逆向
- 结论：**技术上可行，但有两道关卡必须先过；且"接入自己 App"分几个层次，难度差异很大**

---

## 一、先纠正一个常见的误解

很多人以为"设备绑定了官方 App，就必须被官方云端锁死"——**对这块卡来说不是这样的**。

实测 `dumpsys bluetooth_manager` 日志显示，卡片与手机之间的交互是**完全标准的 BLE**：

```
11:58:13.244  BLE-CONNECTED       Get-A78A67  status = Success
11:58:14.550  btif_dm_create_bond  BOND_STATE_NONE        ← Android 系统级配对
11:58:18.290  HID_HOST policy -1 -> 100                  ← 自动挂载标准 HID
11:58:18.290  BATTERY  policy -1 -> 100                  ← 自动挂载标准 Battery
12:02:48.054  BLE-DISCONNECTED    status = Connection Timeout
```

**要点**：
1. 连接走的是 **Android 原生 GATT + 系统 bond**，不是 App 私有的鉴权隧道。
2. 卡片暴露的是**标准服务（HID + Battery）+ 自定义服务（`00009000`）**。
3. 官方 App 用的是**开源插件 `flutter_blue_plus`** —— BLE 层没有任何"魔法"。

**这意味着**：任何能操作 BLE 的程序（Android 原生、iOS、Python/bleak、甚至浏览器）**都能连上这块卡**。硬件层面不排斥第三方。

---

## 二、"绑定"到底绑的是什么？

这是最关键的问题。逆向结果表明：

| 层 | 绑定行为 | 位置 |
|---|---|---|
| **云端绑定** | `POST /voicenotes/mind/app/v1/devices/bind`（带 `pre-check`）| 得到服务器 |
| **账号绑定** | 设备↔得到账号的关联，可"绑定到另一个账户"、可解绑 | 得到服务器 |
| **BLE 绑定** | `btif_dm_create_bond` 系统配对 | 手机系统 |

**关键判断**：绑定主要是**云端/账号层面**的行为，用于：
- 在得到 App 里把录音归到你名下
- 触发云端 ASR 转录、AI 总结、会员权益

**但设备本地功能（录音、存文件、BLE 传文件）本身不依赖云端**——固件里的 `blespp_*` 命令处理**没有任何"token 校验"分支**，只有：
- `blespp_app_get_device_sn_code_handle`（读 SN）
- `blespp_app_notify_device_start_or_stop_recode`（控制录音）
- `blespp_file_get_device_file_list_info_handle`（列文件）
- `blespp_file_set_device_trans_specify_file_handle`（传指定文件）
- `blespp_file_get_device_current_time_handle / set_device_time`（对时）
- `blespp_file_get_device_wifi_status_handle / set`（Wi-Fi 开关）

**没有一条是"鉴权/握手/绑定"命令。** 这是强证据：**设备端不校验账号**。

## 三、能不能接入自己的 App？分三个层次回答

### 层次 1：用自带 App 的"设备控制"—— ✅ 完全可行

你能做到的：
- 扫描发现 `Get-XXXXXX`
- 连接、读电量/固件版本
- **控制录音开始/停止**（`start_or_stop_recode`）
- 读设备文件列表、下载录音文件（`get_file_list` + `trans_specify_file`）
- 给设备对时、开关 Wi-Fi

**依据**：
- 设备端命令处理无鉴权分支
- BLE 层是开源 `flutter_blue_plus`
- 唯一门槛是 `aes_pkcs7_codec`（AES-128 加解密）——**但这是本地算法，一旦知道密钥即可复现**

**唯一未闭环的点**：AES-128 密钥来源。有 3 种可能：
- (a) **固定硬编码 key** → 完美，直接能解密 ✅
- (b) 基于设备 SN/MAC 派生 → 也能算出来 ✅
- (c) 云端绑定时下发 → 需要先绑一次抓取 ⚠️

固件里**没有 ECDH/HKDF/密钥协商字符串**，只有直白的 `aes_128_decrypt ble_reply_data` —— **强烈指向 (a) 或 (b)，即本地可复现**。这是最乐观的信号。

### 层次 2：用自己的后端做转录 + AI 总结 —— ✅ 完全可行

这一层**根本不碰设备**，与 D3200 网页同构：
- 你拿到录音文件 → 传你自己的服务器 → 调 ASR（硅基流动/字节/阿里）→ 调 LLM 总结 → 存你的库
- 没有任何官方依赖

### 层次 3：让设备"完全脱离官方账号"长期使用 —— 🟡 大概率可行，但有一处风险

- 设备端不校验账号 → 理论上解绑后仍能本地录音、本地传文件
- **风险点**：某些功能（如设备端回传的是加密帧）如果密钥是绑定时下发的，解绑后可能无法解密
- **验证方法**：解绑后立刻用自建客户端连一次，看能否读到并解密录音

## 四、决定性验证清单（建议按顺序做）

| 步骤 | 目的 | 方法 |
|---|---|---|
| 1 | 定位 AES 密钥 | 在 `img0.bin` 中反汇编 `aes_128_decrypt` 调用点（字符串 @0xD5FFC），回溯密钥寄存器来源 |
| 2 | 抓一次真实 BLE 会话 | 用 nRF Connect 连 `00009000`，边操作官方 App 边抓包 |
| 3 | 验证无账号可读 | 解绑后，用 Python/bleak 连设备，尝试读 SN/电量/文件列表 |
| 4 | 验证录音可解密 | 录一段音，下载文件，用步骤 1 的密钥试解 |
| 5 | 还原命令帧 | 结合 `ble_command.dart`/`ble_packet_assembler.dart` 的类名与抓到数据对齐 |

**只要步骤 1 得出"密钥本地可得"，自建 App 就成立了。**

## 五、风险与合规提示

- **合规**：这是操作**你自己拥有**的设备（自有硬件互操作研究），解绑也是官方允许的操作，属于合理的自用改造范畴。
- **技术风险**：固件将来可能升级为云端下发密钥（升级后自建客户端失效）。
- **保修/服务**：脱离官方 App 后，官方云端转录、会员权益、OTA 推送都用不了，需自建替代。
- **建议**：保留一台可回退的状态，重要录音多备份。

---

## 六、总体结论

> **可以接入你自己的 App，而且可行性比预想的高。**

理由：
1. 设备连接是**标准 BLE + 开源插件**，无私有鉴权隧道；
2. 设备端命令**没有账号校验**，绑定主要是云端归属行为；
3. 加密是**本地 AES-128**（非 ECDH 协商），固件无密钥协商痕迹，**密钥大概率固定或可派生**。

**剩下的事就一件**：把那个 AES-128 密钥找出来。找到 = 全盘打通；找不到（比如真走云端下发）= 至少"控制 + 状态"这一层还能用。

## 二、为什么两家都"谁都能连"？—— 三个根本原因

### 1. BLE 协议本身是"开放连接"的
BLE 外设（Peripheral）默认向**所有** Central 广播并接受连接。只有当固件**主动要求 bonding / 认证**时，才会拒绝陌生设备。**这是默认值，不是漏洞**。

### 2. 产品 UX 决定了它们不做强制配对
录音豆的产品逻辑是"**开盒即用、App 一键连**"。如果强制走系统蓝牙配对（弹窗、输码），体验会差很多。所以两家都选择：
```
私有 GATT 服务 + 应用层自定义协议 + 免系统配对
```
安克文档 §3.0 明确写着：*"Feishu does not require the user to pair the device in system Settings first."*

### 3. 都是 BES 方案商的参考设计（★重要发现）
两家的 OTA 都使用 **`BEST` magic**（`42 45 53 54`），命令序列**完全同族**：
```
99→9A 协议版本 | 97→98 设置OTA用户 | 8E→8F 硬件信息 | 9D→9E 升级类型
9B→9C 角色ID   | 90→91 选择侧      | 8C→8D 断点续传 | 80→81 镜像大小+CRC32
86→87 配置块   | 85→82 镜像分片    | 88→84 全镜像CRC | 92→93 应用镜像
```
而且**都用 `66666666-6666-6666-6666-666666666666` 作为 OTA 服务**。

> ⇒ 两家都是 **BES（恒玄）芯片**的参考设计，厂商在**应用层**各自定义了产品协议。
> Get 卡片：固件标识 `a622fb2-best1306p_ibrt`（best1306p）
> 安克 D3200：OTA/BES 同族

## 三、协议逐项对比

| 维度 | **Get 笔记卡片** | **安克 D3200 录音豆** |
|---|---|---|
| **发现方式** | 蓝牙名 `Get-XXXXXX` | 广播 service UUID `020cf5da-…`（=产品码 D3200） |
| **免系统配对** | ✅ | ✅ |
| **需要账号/绑定** | ❌ BLE 层不需要（只有云端 HTTP `/devices/bind`） | ❌ 控制层不需要（`0B 87` 绑定是设备级） |
| **控制服务** | `00009100-…-57616c6b697a` | 来自广播的服务 |
| **写特征** | `00009101-…`（CTL_W） | `00007777-0000-1000-8000-00805F9B34FB` |
| **通知特征** | `00009102-…`（CTL_N） | `00008888-0000-1000-8000-00805F9B34FB` |
| **数据/命令服务** | `66666666-…`(命令) + `00009000-…`(数据) | `66666666-…` = **OTA 服务** |
| **帧头（TX）** | `fc fc fc fc` | `08 EE 00 00 00` |
| **帧头（RX）** | `fc fc fc fc`（同） | `09 FF 00 00` |
| **校验** | **CRC32**（`zlib.crc32`，小端 4B） | **和校验**（`Σbytes & 0xFF`，1B） |
| **命令寻址** | 单 16 位 cmd（`0x0043`/`0x0145`/`0x0044`…） | cmdType + cmdId 两字节（`1A 0E`/`1A 07`/`1A 10`…） |
| **载荷风格** | ASCII 文件名 + 小端整数 | 纯二进制结构体 |
| **列文件** | `0x0043` → 文本 `"idx,名,时间,大小;"` | `1A 0E` + page → 二进制（fileId+size 数组） |
| **下载文件** | `0x0145` + 文件名 → `0x0345`(offset+472B 流) | `1A 07` + fileId → `1A 07`(头)/`1A 08`(分片)/`1A 0A`(结束) |
| **删除文件** | `0x0044` + 文件名 | `1A 10` + fileId(u32) |
| **远程录音** | 固件支持（命令未定位） | `18 82` + `01`/`02`（开始/暂停） |
| **时间同步** | `0x0146` + ASCII `YYYYMMDDHHMMSS` | `01 A6` + 4B UTC + 1B 时区 |
| **★ 文件是否加密** | ❌ **完全明文**（Ogg 直传） | ✅ **AES-CTR 加密** |
| **★ 密钥协商** | 仅短命令通道有静态密钥（**与录音无关**） | **ECDH P-256 + HKDF-SHA256**（每次会话） |
| **★ 大文件通道** | 仅 BLE GATT（~25 KB/s） | **Classic SPP** 或 **WiFi SoftAP + WebSocket** |
| **WiFi 配网** | 固件支持，本次未实测 | BLE 下发 SSID/密码（`1A 05`）→ 设备回 IP:port → 手机连 AP 开 WS |

## 四、★ 真正的分水岭：加密

这是两家**本质区别**，也是"网页版难度"的决定因素。

### Get 卡片：录音明文
```
0x0345 → offset(4B) + "OggS....." 原始 Opus 音频
```
我们直接拼出可播放文件，**Ogg CRC 12/12 通过** —— 没有任何加密。

### 安克 D3200：三层加密
```
① 会话密钥: shared = ECDH(appPriv, devPub)          // P-256
             sessionKey = HKDF-SHA256(shared, salt={1,2,3}, info={1,2,3})
② 每文件密钥: fileKeyMaterial = AES-CTR-256(sessionKey, sessionNonce, encryptedFileKey)
             // 明文须以 "soundcored3200"(14B) 开头，余 32B 为文件密钥
③ 分片解密:  AES-CTR，IV = nonce[0..12) ‖ BE_u32(seq*10)，每块 160B
```

**含义：**
- Get 卡片 → **谁连上谁就能听**
- 安克 → 谁都能连，但**没有密钥听不了**（密钥每次会话临时协商）

## 五、为什么 Get 不加密、安克加密？

| | Get 卡片 | 安克 D3200 |
|---|---|---|
| 数据去向 | 主打本地/自有云 | 上传 Anker 云 + 飞书妙记 |
| 安全定位 | "轻"、追求简单 | 用户内容保护 + 品牌合规 |
| 传输优化 | 直接明文推 | 加密 + 专门快传通道 |

两者都是**设计取舍**，不是谁"做错了"。但从隐私角度看，Get 卡片方案**风险显著更高**。

## 六、网页版（Web Bluetooth）实际可行性对比

### Get 卡片 —— ✅ 可直接做（已跑通）
| 需求 | Web Bluetooth 能力 | 结论 |
|---|---|---|
| 连接（免配对） | ✅ | 可 |
| 列文件（明文） | ✅ | 可 |
| 下载文件（BLE GATT） | ✅ | 可 |
| 播放 Ogg | ✅ Chrome 原生 | 可 |

**唯一变量**：设备发 488B 通知，需 MTU ≥ 491（桌面 Chrome 通常能协商到）。

### 安克 D3200 —— ✅ 已跑通（有可运行先例）
| 需求 | 结论 | 实现方式 |
|---|---|---|
| 连接 + 控制 | ✅ | 服务 UUID `020cf5da-…` 精确过滤；写 `00007777-…` / 通知 `00008888-…` |
| 列文件 | ✅ | `1B 0E` + page（分页，每页 10 条） |

| 解密 | ✅ | WebCrypto：ECDH P-256 + HKDF-SHA256 + AES-CTR 原生支持 |

## 七、结论

### 1. "谁都能连"是 BLE 的默认属性，不是漏洞
两家都做了**免配对 + 私有 GATT + 应用层协议**，所以任何 BLE Central（手机、电脑、甚至网页）都能发现并连接。

### 2. 真正的门槛：加密强度 + 传输是否够用
```
Get 卡片:   明文 + 全程 BLE GATT          → 网页版 ✅ 极易（零解密）
安克 D3200: AES-CTR + BLE GATT 也能传     → 网页版 ✅ 可行（需 WebCrypto 解密）
```
**关键修正**：加密**不构成障碍**，因为 WebCrypto 原生支持 ECDH/HKDF/AES-CTR；
只要**数据能经 BLE GATT 拿到**，网页就能解密。

### 3. 网页版真正的边界在哪
| 边界 | 说明 |
|---|---|
| **iOS** | WebKit 无 Web Bluetooth → iPhone 一律不行（唯一硬限制） |
| **Classic BT (SPP)** | 浏览器无此 API → 若某设备**只能**走 SPP，则不行 |
| **WiFi + 自签证书** | 浏览器禁止跳过 TLS 校验 → wss 路径难走 |
| **加密** | ❌ 不是边界（WebCrypto 可解） |

### 4. 对我们的意义
- **先例证明了路径可行**（D3200 这种加密设备都能纯网页做）
- **Get 卡片比它更容易**：无需解密、无需自建 Ogg、无需 ECDH 握手
- 所以"**Get 卡片网页版 + 电脑 Agent 直连**"完全成立

## 九、先例拆解：`recording-bean-web` 是怎么做到的

本机项目 `C:\Users\20195\Documents\ChatGPT\Shawn的项目\recording-bean-web`（已部署 https://recording-bean-web.pages.dev）

**技术栈**：Vite + React + Cloudflare Pages（`wrangler.jsonc` → `pages_build_output_dir: ./dist`）

**核心实现（可直接借鉴给 Get 卡片）**：

| 文件 | 职责 | 对 Get 卡片的可复用性 |
|---|---|---|
| `src/direct/bluetoothDiscovery.js` | 按服务 UUID 精确过滤 / acceptAllDevices 兜底 | ★ 直接照搬（换 UUID 与 namePrefix） |
| `src/direct/protocol.js` | 组帧 + `PacketBuffer` **分片重组** + 校验 | ★ 思路可搬（换 `09 FF` → `fc fc fc fc` + CRC32） |
| `src/direct/crypto.js` | WebCrypto ECDH/HKDF/AES-CTR | **Get 卡片不需要**（明文） |
| `src/direct/oggOpus.js` | 裸 Opus 帧 → 自建 Ogg 页；`AudioContext` 转 WAV | **Get 卡片不需要 mux**（设备已发完整 Ogg）；WAV 转换可留 |
| `src/direct/d3200BrowserClient.js` | 会话状态机、进度、导出、删除 | ★ 状态机结构可搬 |

**关键技术点（都已验证可行）**：
1. **通知分片重组**：`PacketBuffer.feed()` 累积多包、按 `09 FF 00 00` 找头、按 length 字段切包、校验通过才收 —— 证明**浏览器完全能处理几百字节的 BLE 通知**
2. **写入降级**：`writeValueWithoutResponse` 优先，否则 `writeValue`
3. **等待模式**：`#waitFor(predicate, timeout, label)` 把"发命令 → 等特定应答"封装成 Promise
4. **导出流程**：`1A 07` 请求 → 等 `1A 07`(头含密钥)/`1A 08`(分片)/`1A 0A`(完成) → 解密拼接 → 装 Ogg → 转 WAV
5. **删除**：`1A 10` + fileId，检查 `packet.status`

**部署方式**：`pnpm build` → `npx wrangler pages deploy dist --project-name <name>`

> ⇒ 做 Get 卡片网页版，可以直接把这套骨架搬过来，
> **去掉 crypto 和 Ogg mux 两块**，把协议层换成 `fc fc fc fc` 帧 —— 工作量比 D3200 小得多。

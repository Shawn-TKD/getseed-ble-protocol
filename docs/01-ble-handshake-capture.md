## 二、GATT 通道结构（本次会话实测）

| Handle | 方向 | 用途 | 是否加密 | 实测包数 |
|---|---|---|---|---|
| `0xA002` | Device → App (Notify) | **明文命令/状态通道** | ❌ 明文 | 159 |
| `0xA102` | App → Device (Write Cmd) | 加密数据下行 | ✅ AES | 22 |
| `0xA105` | Device → App (Notify) | 加密数据上行 | ✅ AES | 22 |
| `0xA202` | App → Device (Write Cmd) | `fcfcfcfc` 封装控制通道（下行） | ⚠️ 明文帧头 + CRC | 13 |
| `0xA205` | Device → App (Notify) | `fcfcfcfc` 封装控制通道（上行） | ⚠️ 明文 + CRC | 15 |

另有标准 GATT 发现流量（handle `0x0000`，READ_BY_TYPE/FIND_INFO，属 HID Battery 等系统服务）。

## 三、通道一：`0xA002` 明文命令通道（设备 → App）

**帧格式（little-endian）：**
```
+--------+--------+--------+------------------+
| cmd 1B | len 2B | payload (len bytes)       |
+--------+--------+--------+------------------+
```

**实测命令表：**

| cmd | len | payload | 语义推断 |
|---|---|---|---|
| `0x7C` | 1 | `00` | 会话/链路查询 |
| `0x81` | 10 | `0000 "BEST" 01000100` | 能力握手（BEST 标识 + 版本位） |
| `0x83` | 5 | `000001 xxxxxxxx` | **心跳/随机数**（150 条，4B 随机全不同） |
| `0x84` | 1 | `00` | 确认 |
| `0x87` | 1 | `00` | 确认 |
| **`0x8D`** | **40** | `000000000000` + **32B 高熵值** | **★ P-256 公钥 / 密钥交换材料** |
| **`0x8F`** | **36** | `0000 "BEST" 00000001 00000000 00 "a622fb2-best1306p_ibrt"` | **★ 设备身份 + 固件版本** |
| `0x93` | 1 | `00` | 确认 |
| `0x98` | 1 | `00` | 确认 |
| `0x9A` | 4 | `00000000` | 状态位图（全 0 = 空闲） |

### 3.1 公钥证据（cmd 0x8D）
```
00000000 0000 379c0065 ca2f94f9 5ec3288d f156bb20
85ea4fb4 197ee247 ac1176db 40a50a6f bf38267c
       └──────────── 32 字节高熵数据 ────────────┘
```
- 32 字节 = **P-256 曲线 X 坐标长度**，与 App 侧 `pointycastle.ECCurve_prime256v1` 完全吻合。
- 该值在整个 4.3MB 抓包中**只出现 1 次** → 典型的一次性 ECDH 公钥特征。

### 3.2 固件身份证据（cmd 0x8F）
```
0000 42455354 00000001 00000000 00
     └"BEST"┘
61363232 6662322d 62657374 31333036 705f6962 7274 00
└─────── "a622fb2-best1306p_ibrt" ──────┘
```
- `BEST` 是 BES 芯片厂的魔数（与 OTA 通道一致）。
- `a622fb2-best1306p_ibrt` = 固件分支/构建标识 → 印证 `cust/mivi_ai_recorder` + best1306p。

## 四、通道二：`0xA102` / `0xA105` 加密数据通道

**实测：22 次写入 vs 22 次通知，全部为 16 字节整块。**

### 4.1 ★ 决定性证据：密文重复

| 方向 | 密文（hex） | 出现次数 |
|---|---|---|
| W→ (`A102`) | `8db70aadce8fa250492f38b063b2054f` | **12** |
| W→ | `77019a44159539ab45e67147f75845ea` | **12** |
| W→ | `a790c594a02da88582558c3b42b577d1` | 1 |
| W→ | `ad44e938a0e67d1df257c503b1fe18c9` | 5 |
| ←N (`A105`) | `ee35aa319da264fbd96cde30ec8e13ad` | 2 |
| ←N | `115afd4dead41fe1a333936c13aa060b` | **12** |
| ←N | `5ab7e62eb13d0b160a80902c1b2bfb2e` | 1 |
| ←N | `98057e8c5c40e312664c9cf2dc644811` | 5 |
| ←N | `0e83879154aacbed3e8568d23f1c2a02` | 2 |

**推理：**

```
若为 CTR / 随机 IV → 相同明文必然产生不同密文（密文全唯一）
实测       → 相同位置反复出现同一密文（x12、x5 …）
∴ 加密模式 ∈ { ECB, 固定 IV 的 CBC, 固定 nonce 的 CTR }
```

由于密文块恰好 **16 字节对齐**、且**请求↔响应密文一一配对**，最可能是 **AES-128-ECB**（或对每个命令用固定的 16B 固定明文 -> 固定密文）。

### 4.2 请求/响应配对（时间对齐后）
```
t+195ms  A102-w 8db70aad...  →  t+292ms  A105-n ee35aa31...
t+488ms  A102-w 77019a44...  →  t+585ms  A105-n 115afd4d...
t+1218ms A102-w a790c594...  →  t+1414ms A105-n 5ab7e62e...
t+10846ms A102-w ad44e938... →  t+10920ms A105-n 98057e8c...
```
典型的**短命令 request/response**（如"读状态""拉一帧"）。

## 五、通道三：`0xA202` / `0xA205` 封装控制通道（明文）

**帧格式（big-endian len/cmd，带 4 字节尾校验）：**
```
+----------+--------+--------+---------+--------+
| magic 4B | len 2B | cmd 2B | body    | crc 4B |
| fcfcfcfc | BE     | BE     | len B   | ?      |
+----------+--------+--------+---------+--------+
```

**实测帧：**

| 方向 | cmd | len | body | 语义 |
|---|---|---|---|---|
| W→ | `0x0146` | 14 | `"202610101158 20"` + 4B | **同步时间戳**（ASCII 年月日时分秒） |
| W→ | `0x5000` | 13 | `00000000000000000000000000` | 查询（空） |
| W→ | `0x4300` | 8 | `0100000005000000` + 4B | 参数设置 |
| ←N | `0x5000` | 13 | `000000...` + 4B | 查询响应 |
| ←N | `0x4000` | 1 | `00` | 状态 |
| ←N | `0x4100` | 1 | `01` | 状态 |
| ←N | `0x4600` | 1 | `01` | 时间设置 ACK |

**时间戳帧可完全解出：**
```
fcfcfcfc 4601 0e00 3230323631303130313135383230 fdecf8ea
         │    │    └"20261010115820"（2026-10-10 11:58:20）
         │    └len=0x000e=14
         └cmd=0x0146
```
（注：`4601` 小端读作 0x0146；len `0e00` 小端 = 14 —— 此通道为 **little-endian**，与 A002 一致，修正上表字节序描述。）

CRC 未匹配 `zlib.crc32(body)` 的任何常见变体（试过 body / magic+len+body / len+body）→ 可能是 **CRC32 加初值/异或**（BES 常用 `crc32_be` + `^0xFFFFFFFF`）或校验前先拼别的字段。**待定项**。

## 七、仍未闭合的 3 个点 & 下一步

1. **AES 模式精确判定（ECB vs CBC-fixedIV）** —— 需要**已知明文**做验证。可行做法：控制通道 `0xA202` 里，App 发送的 `0x0146` 时间戳帧是**明文可读**的；若某次该时间戳**同时**出现在 A102 加密通道（即"加密版"），即可直接对齐明文，判定 ECB/CBC。当前抓包未出现此情形。
2. **IV/Nonce 来源** —— 怀疑来自 `0x83` 心跳的 4B 随机数（150 条，一直在变）。需在**同一会话内**比对心跳值变化 与 密文变化 的相关性。
3. **App→Device 的公钥**（本地生成的那把）—— 本次抓包只抓到**设备→App** 的 `0x8D`；App 侧公钥应走 A102 加密通道或以明文走别的 cmd。需要**从连接建立的第一秒**开始抓。

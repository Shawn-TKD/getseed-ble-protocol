# 得到笔记卡片 — 协议/固件 深度结论报告

> 基于 3 份 btsnoop 抓包（4.3MB + 871KB + 39KB）+ 0.1.8 固件字符串 + libapp.so 字符串的交叉分析

---

## 一、核心问题：通信到底用没用密钥？

### 结论：**读取录音完全不需要密钥** ✅

| 通道 | Handle | 用途 | 加密状态 | 证据 |
|---|---|---|---|---|
| **设备信息** | `0xA002` | 固件版本、P-256 公钥、心跳 | ❌ **明文** | `"BEST"`、`a622fb2-best1306p_ibrt` 直接可读 |
| **短命令** | `0xA102`/`0xA105` | 握手、状态轮询（16B 定长块） | ✅ **加密** | 16 字节整块，高熵 |
| **控制+文件** | `0xA202`/`0xA205` | 命令 + **录音文件传输** | ❌ **明文** | 文件名、`OggS` 直接可读，CRC32 可校验 |

**录音数据在 `0xA205` 上是明文 Ogg**，重建后 Ogg 页 CRC **12/12 通过、零缺失** —— 这证明它没有经过任何加密变换。

## 二、那 4 个"16 字节密文块"是什么？

### 决定性实验：全二进制搜索

| 目标文件 | 搜索 4+5 个 16 字节块 | 结果 |
|---|---|---|
| `libapp.so` (29.8 MB) | 正序 + 反序 | **全部未命中** |
| `libflutter.so` (10.7 MB) | 正序 + 反序 | **全部未命中** |
| `fw_0.1.8_img_f6.bin` (1.6 MB) | 正序 + 反序 | **全部未命中** |
| （对照组）`fcfcfcfc` | — | ✅ 命中 @ `0x17F5A8` |

**判读：**
```
未命中 + 对照组命中（证明搜索方法有效）
  ⇒ 这些 16 字节块不是硬编码常量，而是运行时计算出来的加密输出
  ⇒ 短命令通道 (0xA102/0xA105) 确实用了密钥
```

**但关键点：** 该通道**不承载任何录音数据**，只用于握手/心跳。

### 为什么密文跨会话完全相同？

| 会话 | A102 unique | A105 unique | 交集 |
|---|---|---|---|
| 会话1 (13:17) | 4 | 5 | — |
| 会话2 (13:27) | 3 | 3 | **3 / 3** |
| 会话3 (14:42) | 4 | 3 | **全部命中** |

```
相同明文 + 相同密钥 → 相同密文（确定性）
若为每次协商的临时 ECDH → 密文必然每次不同（实测相同）
  ⇒ 密钥是「静态/预共享」，或每次协商结果恒定
```

这与 `0xA002` 通道明文传输的 **P-256 公钥** 对应 —— 若是**静态密钥对**（固件里写死私钥），则每次 DH 结果恒定，密文自然相同。

## 三、★ 新发现：固件暴露的完整能力清单

从 0.1.8 固件字符串提取的 `blespp_*` 命令处理器：

| 固件函数 | 能力 | 是否已被我们用到 |
|---|---|---|
| `blespp_file_get_device_current_time_handle` | 获取时间（cmd `0x0146`） | ✅ 已解 |
| `blespp_file_set_device_time_handle` | 设置时间 | ✅ |
| `blespp_file_get_device_wifi_status_handle` | 查询 WiFi 状态（`0x0050`） | ✅ |
| **`blespp_device_set_msd_mode_status`** | **★ 切换到 U盘(MSD)模式** | ❌ **未用** |
| **`blespp_device_get_msd_mode_status`** | 读取 MSD 模式 | ❌ 未用 |
| `common_set_msd_mode_status_to_flash` | MSD 状态**持久化到 Flash** | ❌ |
| **`blespp_file_set_device_delete_specify_file_handle`** | **★ 删除指定文件** | ❌ |
| **`blespp_file_set_device_clear_all_file_handle`** | **★ 清空所有文件** | ❌ |
| **`blespp_app_notify_device_start_or_stop_recode`** | **★ 远程开始/停止录音** | ❌ |
| `blespp_app_get_device_sn_code_handle` | 获取设备 SN | ❌ |
| `blespp_file_trans_interrupt_handle` | 中断传输 | ❌ |
| **`blespp_file_set_device_special_wifi_status_handle`** | **★ 设置 WiFi 快传状态** | ❌ |
| `blespp_file_device_notify_app_wifi_status` | 通知 App WiFi 状态 | ❌ |
| `blespp_app_cmd_replay_handle` | 命令重放 | ❌ |
| `app_filepath_server_mtu_exchanged` | MTU 协商 | ✅（被动） |
| `app_ble_ai_file_data_sent_done` / `receive_data_done` | 文件传输完成回调 | ✅ |

**★★ 最重要的两个发现：**

### 1. 设备**支持 U盘模式（MSD）**
`blespp_device_set_msd_mode_status` + `common_set_msd_mode_status_to_flash`

> 这解释了为什么你插电脑时**期待它变成U盘** —— 它**确实有这个能力**，只是需要**先通过 BLE 发命令切换模式**！默认不在 MSD 模式，所以插 USB 只充电不枚举。

### 2. **WiFi 快传确实存在**
`blespp_file_set_device_special_wifi_status_handle` / `..._notify_app_wifi_status`

> 传输录音时，设备可以通过 BLE 把 WiFi 状态（SSID等）告知 App，然后走 WiFi 走大文件。这就是 0.1.8 更新日志里的"WiFi 快传优化"。

## 四、完整命令码表（实测 + 固件对照）

### 控制通道 `0xA202`(手机→设备) / `0xA205`(设备→手机)

| cmd | 方向 | body 结构 | 语义 |
|---|---|---|---|
| `0x0041` | →/← | 空 / `01` | 命令/ACK |
| `0x0042` | ← | `01000000` + `8078a403`(=61,111,424) + `000c0000`(=3072) | **疑似容量/存储信息** |
| `0x0043` | →/← | 请求 `0100000005000000` / 响应 `idx,名,时间,大小;` | **文件列表** |
| `0x0044` | →/← | `文件名` / `01` | **文件回执**（可能=标记已同步） |
| `0x0050` | →/← | 空 / 13×`00` | 状态查询 |
| `0x0140` | ← | `00` | 状态 |
| `0x0145` | → | `00000000` + `文件名` | **请求下载** |
| `0x0146` | →/← | `YYYYMMDDHHMMSS` / `01` | 时间同步 |
| `0x0147` | ← | `01 01 00 ef01`（`ef01`=**495 = MTU**） | **MTU 上报** |
| `0x0150` | ← | `state,seq,offset(4LE),0,文件名` | **传输进度**（offset 递增至文件大小） |
| `0x0245` | ← | `size(4 LE)` | 文件大小 |
| `0x0345` | ← | **`offset(4 LE)` + 472B 数据** | **★ 文件数据块** |
| `0x0445` | ← | `size(4 LE)` | 传输结束 |

### 设备信息通道 `0xA002`（明文）

| cmd | body | 语义 |
|---|---|---|
| `0x7C` | `00` | 握手开始 |
| `0x81` | `0000 "BEST" 01000100` | 能力协商 |
| `0x83` | `000001` + 4B 随机 | **心跳/随机数**（150+ 条，全不同） |
| `0x84`/`0x87`/`0x93`/`0x98` | `00` | ACK |
| **`0x8D`** | 6B保留 + flag + **32B P-256 公钥** | ★ 设备公钥 |
| **`0x8F`** | `"BEST"` + `"a622fb2-best1306p_ibrt"` | ★ 固件身份 |
| `0x9A` | `00000000` | 状态位图 |

## 五、隐私/安全扫描：BLE 通道有没有泄漏敏感信息？

**扫遍所有抓包 body 的可打印字符串：**

| 类型 | 结果 |
|---|---|
| URL (`http://`, `://`, `www.`) | ❌ **未发现** |
| WiFi SSID/密码 | ❌ **未发现**（固件里的 SSID/password 串是 wpa_supplicant 标准配置项，非实际凭据） |
| Token / secret / API key | ❌ **未发现** |
| 账号 / 手机号 | ❌ **未发现** |
| 录音文件名 / 时间 / 大小 | ✅ 明文可见 |
| 固件版本 / 型号 | ✅ 明文可见 |

**结论：BLE 通道不泄漏云账号凭据，但泄漏录音元数据与内容本身。**
